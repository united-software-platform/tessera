# Design

## Context

Состояние до изменения — по обзору носителей 2026-11-26; мотивация — в `proposal.md`.

- **Смешения предмета.** README плагина несёт разделы разработки («Как расширять», «Проверка»,
  пункт о `scripts/bootstrap.sh`). `AGENTS.md` не отделяет правила-содержание продукта
  от правил-норм работы. Слово «разработчик» называет обе роли: в спеке `plugin-dependencies` —
  потребителя, в `AGENTS.md` и `CONTRIBUTING.md` — контрибьютора. Ни один носитель предмет
  не объявляет.
- **Локальная регистрация.** `scripts/bootstrap.sh` связывает четыре навыка плагина
  относительными симлинками в известных каталогах проекта или по произвольному пути.
  Зависимостей, лаунчера, области `user` и прочих харнесов в нём нет.
- **Скрипт поставки.** Всегда ставит tessera из ветки `main` (спека `delivery`, «Одна команда
  ставит tessera»), а область `project` требует tessera в составе («Проектная область требует
  tessera в составе»). Условие задачи TSS-020 запрещает его менять.
- **Окружение репозитория.** Каталоги регистрации харнесов (`.zcode/`, `.agents/`, `.claude/`)
  вне индекса git. `AGENTS.md` ссылается на правила в дереве. `mise.toml` закрепляет только
  openspec CLI; задач mise в репозитории нет.
- **Нормы окружения.** Инструментарий и задачи — через mise, задачи идемпотентны
  ([ENV-001](../../../plugins/tessera-plugin/rules/environment.md#инструментарий-env-001),
  [ENV-006](../../../plugins/tessera-plugin/rules/environment.md#задачи-env-006)).
- **mise.** Аргументы после `--` доходят до скрипта задачи; без `--` флаги съедает сам mise.

Ограничение на всё решение: `scripts/install.sh` не меняется.

## Goals / Non-Goals

**Goals:**

- Агент различает предмет прочитанного по самому описанию; расхождение ловится проверкой.
- Норма класса «Плагины» читается и потребителем — в поставке, и контрибьютором — в репозитории;
  второй класс заводится без перенумерации норм первого.
- Контрибьютор готовит харнесы одной командой в любом поддерживаемом харнесе и в любой области;
  навыки плагина видны из рабочего дерева.
- Расхождение копии механики с оригиналом ловится проверками.

**Non-Goals:**

- Общая библиотека механики для двух скриптов: она требует правки `scripts/install.sh`.
- Реестр локальной настройки, закрепление версий зависимостей, установка харнесов
  и инструментов — инструменты ставит `mise install`.
- Порядок разработки самого tessera как документ правил: его предмет — «разработка продукта»,
  и несут его `AGENTS.md` и `CONTRIBUTING.md`.

## Decisions

### 1. Нормы классов ПО — новый документ с серией кодов на класс

Файл `plugins/tessera-plugin/rules/software-class-rules.md`, заголовок «Нормы классов ПО», префикс
кодов `PLG`. Документ назван по назначению, а не по первому классу: имя вроде `plugin-rules.md`
стало бы ложным с появлением второго класса.

Нормы ведутся по классам ПО; у класса своя серия кодов и свой раздел. Сейчас класс один —
плагины, ПО, поставляющее что-либо куда-либо. Нормы класса «Плагины» о предмете описания:

| ID | Норма |
|----|-------|
| PLG-001 | Описания для агентов принадлежат ровно одному предмету: «продукт» — уровень предмета (что описывается, поведение компонента) либо «разработка продукта» — уровень работы над предметом (как он создаётся: правила и процесс) |
| PLG-002 | Предмету соответствует роль: «продукт» читает потребитель, «разработка продукта» — контрибьютор; слово «разработчик» роль не называет |
| PLG-003 | Описание для агентов открывается объявлением предмета — единственной канонической строкой сразу после заголовка; для README с блоком бейджей — после блока |
| PLG-004 | Объявленный предмет соответствует носителю: артефакты плагина и описания продукта для потребителя объявляют «продукт»; точка входа агентов репозитория, `CONTRIBUTING.md` и глоссарий — «разработку продукта» |
| PLG-005 | Артефакт обслуживает ровно один предмет: материал другого предмета выносится в носитель своего предмета, в источнике остаётся ссылка |
| PLG-006 | Навык описывает только поведение продукта; порядок подготовки харнесов к работе над репозиторием живёт вне навыка — в точке входа агентов и `CONTRIBUTING.md` |
| PLG-007 | Правила плагина описывают только поведение продукта; точка входа агентов объявляет их нормы, принятые для работы над репозиторием |
| PLG-008 | Объявление предмета у каждого носителя сверяется проверкой проекта |

Документ строится по образцу прочих правил: заголовок, объявление предмета, назначение,
навигация, таблица норм по классам, понятия, границы нормы, разделы норм, версионирование.
Новый класс ПО заводится своим разделом и своей серией кодов, когда появляется ПО, к которому
действующие нормы не подходят.

Альтернативы:

- `DOC-025`…`DOC-026` в `documentation-rules.md` — отклонена владельцем: это правило об оформлении
  проектной документации, а разделение предмета — смысловая часть разработки ПО.
- `DGN-013`…`DGN-015` в `project-docs-rules.md` — отклонена владельцем: норма документа-жанра
  для трёх документов людей.
- Внутренняя норма без правила плагина — отклонена: нормы применяются и к самому tessera,
  и к поставке из него.

### 2. Объявление предмета — канонические строки

Две строки, дословно:

```markdown
**Предмет:** продукт — уровень предмета: что описывается, поведение компонента.
**Предмет:** разработка продукта — уровень работы над предметом: как этот предмет создаётся, правила и процесс.
```

Положение — первая содержательная строка после заголовка первого уровня. YAML-фронтматтер
не считается; для README строки блока бейджей — изображения и ссылки, начинающиеся с `![` или `[![`,
— не считаются. В описании объявление одно.

Строки совпадают дословно у всех носителей, поэтому сверяются простым сравнением, а агент
читает уровень прямо из строки.

### 3. Носители и изъятия

| Носитель | Предмет |
|----------|---------|
| `plugins/tessera-plugin/rules/*.md`, навыки `plugins/tessera-plugin/skills/*/SKILL.md`, README плагина | продукт |
| `README.md`, `docs/use-cases.md` — описания продукта для потребителя | продукт |
| `AGENTS.md`, `CONTRIBUTING.md`, `GLOSSARY.md` — работа над продуктом | разработка продукта |

Объявления не несят файлы, не являющиеся описаниями: шаблоны операций (заготовки порождения,
их предмет объявляет навык, который ими пользуется), манифесты и каталог маркетплейса,
спецификации и изменения OpenSpec, беклоги, сценарии. Служебные элементы файла — заголовок,
назначение, навигация, таблица версий — предмета не описывают.

### 4. Устранение смешаний

- **README плагина** теряет разделы «Как расширять» и «Проверка» и пункт о локальной регистрации;
  они переходят в `CONTRIBUTING.md` — разделом «Расширение плагина» и разделом «Проверки».
- **`AGENTS.md`** получает раздел «Предметы описания»: репозиторий — предмет «разработка продукта»;
  правила и навыки плагина — содержание продукта, принятое для работы над репозиторием как нормы;
  их правка — изменение продукта и идёт через OpenSpec.
- **`README.md`**: предложение о разработке через OpenSpec переформулировано как граница поставки —
  каталог в поставку не входит; порядок работы над репозиторием отнесён к `CONTRIBUTING.md`.
- **`reading-rules.md`**: упоминание «репозитория kit'а» заменено нейтральным — чужой контекст
  в правиле продукта.

Навыки не меняются по существу: отказ навыка с командой скрипта поставки — поведение продукта,
одинаковое для потребителя и контрибьютора. Порядок подготовки харнесов контрибьютора живёт
в `AGENTS.md` и `CONTRIBUTING.md`.

### 5. Слова ролей

| Где | Было | Станет |
|-----|------|--------|
| Спека `plugin-dependencies`, требование о зависимостях | разработчик | потребитель; заголовок требования переименован |
| `AGENTS.md`, `CONTRIBUTING.md`, `GLOSSARY.md`, спека `framework-essence` — о работе над репозиторием | разработчик, правящий репозиторий или плагин | контрибьютор |
| Спека `continuous-integration` | правящий репозиторий | контрибьютор |
| `rules/git-rules.md`, `rules/ddd.md` — «агент или разработчик», «аналитики, разработчики и заказчики» | разработчик | без изменений: общее слово, не роль |

### 6. Глоссарий — один контекст, две роли

`GLOSSARY-MAP.md` не заводится: хранилище, лаунчер и область установки общие у поставки
и локальной настройки, а работа над продуктом — уровень работы над той же моделью. Статьи:

| Статья | Вид | Текст |
|--------|-----|-------|
| Контрибьютор (Contributor) | роль | Тот, кто правит tessera в её репозитории — меняет исходники, проверки и порядок выпуска, — и подготавливает для этого свои харнесы локальной настройкой. _Avoid_: разработчик, пользователь, правящий систему, сопровождающий |
| Класс ПО (Software Class) | сущность | Множество продуктов одной природы, к которому относятся нормы класса; сейчас один класс — плагины, ПО, поставляющее что-либо куда-либо. _Avoid_: тип ПО, вид ПО, категория |
| Предмет описания (Description Subject) | объект-значение | То, что описывает описание для агентов: **продукт** либо **разработка продукта**; каждое описание принадлежит ровно одному предмету. _Avoid_: назначение, роль, тема |
| Продукт (Product) | объект-значение | Предмет описания «продукт»: то, что получает потребитель — поведение компонента; уровень предмета — что описывается. _Avoid_: изделие |
| Разработка продукта (Product Development) | объект-значение | Предмет описания «разработка продукта»: как создаётся продукт — правила и процесс; уровень работы над предметом. _Avoid_: проектная разработка, процесс |
| Локальная настройка (Local Setup) | доменная служба | Подготовка харнесов контрибьютора к работе над репозиторием: регистрирует навыки плагина из рабочего дерева, приносит зависимости в хранилище и ставит лаунчер — в заданной области установки; tessera для самой себя не ставится. _Avoid_: установка зависимостей, настройка среды, bootstrap, инициализация |

Правки действующих статей:

- «Потребитель»: в Avoid добавлен «разработчик».
- «Область установки»: определение обобщено — куда связываются навыки: пользовательские каталоги
  харнесов (`user`) или каталоги навыков текущего проекта (`project`); в области project поставка
  ещё подключает правила; английское имя статьи — Scope.
- «Хранилище»: повторный запуск поставки или локальной настройки доводит клоны до ветки `main`.
- «Регистрация»: механизм скрипта поставки и локальной настройки — без слова «разработчик».
- «Установка»: в Avoid добавлена «локальная настройка».

### 7. Локальная настройка — копия механики поставки со сторожем

`scripts/setup.sh` — самостоятельный сценарий: копия механики `scripts/install.sh`, где навыки
плагина берутся из рабочего дерева, а компонентами служат только зависимости.

Альтернативы:

- **Композиция** — неизменённый `scripts/install.sh` ставит состав, короткий сценарий перевязывает
  навыки плагина. Отклонена: поставка обязана приносить tessera, значит в хранилище появится клон
  `main`, реестр поставки опишет прежние цели, а отчёт поставки на каждом запуске назовёт навыки
  плагина чужими. Состав из одних зависимостей в области `project` поставка отвергает.
- **Общая библиотека** — вынести механику в подключаемый файл. Отклонена: требует правки
  `scripts/install.sh`.
- **Выборка текста функций из `scripts/install.sh` во время выполнения.** Отклонена: скрытая
  связность с двумя десятками глобальных переменных, поломка видна только в прогоне.
- **Перенаправление адреса на локальное зеркало**, как в `scripts/check.sh`. Отклонена: даёт снимок
  фиксации, а не рабочее дерево.

Цена копии — общие блоки в двух файлах. Её платит сторож в `scripts/check.sh` (решение 11);
прецедент — зеркальные манифесты плагина с проверкой `manifests_identical`.

### 8. Устройство `scripts/setup.sh`

- **Таблицы.** `COMPONENTS` — только строки зависимостей (formular, mattpocock-skills), дословно
  из `scripts/install.sh`; `HARNESSES` — дословная копия. Навыки плагина — каталог
  `plugins/tessera-plugin/skills` рабочего дерева.
- **Общие функции** — дословные копии из `scripts/install.sh`: пути и таблицы, отбор харнесов
  и каталоги назначения, хранилище и клоны, сбор навыков и ссылки, лаунчер. Реестра локальная
  настройка не пишет, поэтому построение JSON не переносится. Перечень общих функций —
  в `scripts/check.sh`.
- **Отличия от оригинала.** `link_is_ours` — своя ссылка та, чья разрешённая цель лежит в хранилище
  или в навыках плагина рабочего дерева; сбор навыков плагина; самопроверка и отчёт без правил;
  поток установки и удаления; параметры.
- **Общее с поставкой.** Хранилище `~/.local/share/tessera/` и лаунчер `~/.local/bin/backlog`:
  обёртка лаунчера пишется дословно той же, поэтому обе стороны считают её своей. Локальная
  настройка ничего не снимает из хранилища и не клонирует tessera.

Цель ссылки проверяется после разрешения: относительные ссылки `scripts/bootstrap.sh`
разрешаются в рабочее дерево, признаются своими и пересоздаются абсолютными — переезд
с прежнего механизма происходит без ручной чистки.

Поток установки: параметры → отбор харнесов → каталоги назначения → клоны зависимостей
в хранилище → навыки зависимостей и навыки плагина → ссылки → лаунчер → самопроверка → отчёт
→ напоминание перезапустить сессию харнеса. Диалога, реестра и подключения правил нет.

Поток удаления: снимаются ссылки навыков плагина в каталогах выбранной области; в области
`project` без `--plugin-only` — ещё и ссылки зависимостей в каталогах репозитория. Хранилище
и лаунчер не трогаются — их снимает `scripts/install.sh --uninstall`.

| Параметр | Действие | Умолчание |
|----------|----------|-----------|
| `--scope project\|user` | область установки | `project` |
| `--plugin-only` | только навыки плагина: без зависимостей, хранилища и лаунчера — и при установке, и при удалении | — |
| `--harness <список>` | ограничить харнесы через запятую | все найденные |
| `--skills-dir <путь>` | дополнительный каталог навыков | — |
| `--uninstall` | снять ссылки локальной настройки | — |
| `-h`, `--help` | справка | — |

Коды возврата как у скрипта поставки: `0` — выполнено и прошла самопроверка либо ничего
не требовалось; `1` — харнесы не найдены, источник не получен или самопроверка не пройдена;
`2` — ошибка в параметрах.

Ссылки абсолютные, как в поставке: после переноса клона настройку повторяют.

### 9. Область установки: умолчание `project`

Умолчание отличается от поставки (`user`) по трём причинам:

- несколько клонов и worktree: в области `user` все они смотрят одно рабочее дерево, и навыки
  ветки одного клона видны в другом;
- изоляция: в области `project` настройка не затрагивает другие проекты того, кто одновременно
  применяет tessera как потребитель;
- преемственность: `scripts/bootstrap.sh` регистрировал навыки в каталогах проекта.

Хранилище и лаунчер в любой области пользовательские — как у поставки. В области `user` рабочее
дерево заменяет `main` для всех проектов машины; удаление или перенос клона оставляют
пользовательские ссылки висячими до повторной настройки.

### 10. Один вход: `scripts/setup.sh` заменяет `scripts/bootstrap.sh`

Два механизма регистрировали бы одни навыки с разной семантикой: `scripts/bootstrap.sh`
пишет относительные ссылки и заменяет элемент независимо от того, кем он создан; сценарий
настройки пропускает чужие элементы и называет их. Оставляется один — `scripts/setup.sh`;
сценарий «только навыки плагина» покрывает флаг `--plugin-only`.

Задача mise в `mise.toml`:

```toml
[tasks.setup]
description = "Локальная настройка: навыки плагина из рабочего дерева и зависимости — в харнесы контрибьютора"
run = "scripts/setup.sh"
```

Аргументы передаются после `--`: `mise run setup -- --scope user`. Харнесы задача не закрепляет
и не ставит ([ENV-001](../../../plugins/tessera-plugin/rules/environment.md#инструментарий-env-001)).

### 11. Проверки

Все проверки — в `scripts/check.sh`, как прежде.

- **Сверка объявления предмета.** Носители и ожидаемый предмет — таблицей в скрипте: объявление
  стоит на своём месте, единственно, канонично и соответствует носителю.
- **Сторож общих блоков.** Текст каждой общей функции извлекается из обоих скриптов и сравнивается;
  таблица `HARNESSES` сравнивается целиком; строки `COMPONENTS` сценария настройки должны как
  множество совпадать со строками `COMPONENTS` скрипта поставки без tessera — так ловится
  и правка, и появление новой зависимости.
- **Статические проверки сценария.** Синтаксис, справка, отвержение неверных параметров кодом `2`.
- **Дымовые прогоны.** Полная настройка, `--plugin-only`, `--uninstall` и область `user` —
  в поддельном домашнем каталоге; зависимости клонируются из своих репозиториев, навыки плагина —
  из рабочего дерева проверок. Прогоны делят поддельный домашний каталог, чтобы клоны
  не повторялись.

«`scripts/install.sh` не изменён» — разовая сверка при ревью: `git diff main -- scripts/install.sh`
пуст. Постоянной проверкой она не становится: заблокировала бы правомерные будущие правки.

## Risks / Trade-offs

- [Копия механики расходится с оригиналом] → сторож общих блоков останавливает проверки; правка
  общей функции вносится в оба файла одной правкой.
- [Сторож не видит новую функцию оригинала, которую копия должна перенять] → дымовые прогоны;
  перечень общих функций пополняется вместе с оригиналом.
- [Объявление предмета читают агенты потребителя в копиях правил] → строка одна и короткая,
  её смысл объяснён в правиле, которое поставляется вместе с ней.
- [В области `user` рабочее дерево заменяет `main` во всех проектах] → умолчание `project`;
  последствие названо в `CONTRIBUTING.md`.
- [`scripts/install.sh --uninstall` снимает хранилище, лаунчер и ссылки зависимостей, созданные
  локальной настройкой] → ссылки зависимостей возвращаются повторным запуском; порядок назван
  в `CONTRIBUTING.md`.
- [Зависимости уже стоят плагином маркетплейса, и полная настройка дублирует их навыки ссылками] →
  `--plugin-only`; случай назван в `CONTRIBUTING.md`.
- [Полная настройка требует сети: клоны зависимостей] → `--plugin-only` работает без сети.
- [Снятие `scripts/bootstrap.sh` ломает привычную команду] → **BREAKING** отмечено в предложении;
  `AGENTS.md` и `CONTRIBUTING.md` называют новый вход той же правкой.
- [Число правил плагина выросло до девяти] → места, называющие число, перечислены в задачах;
  поставка берёт перечень правил из клона и правки скрипта не требует.

## Migration Plan

Применение идёт двумя фазами, каждая оставляет `scripts/check.sh` зелёным:

1. Предмет описания: правило класса → глоссарий → объявления → устранение смешаний и слова
   ролей → сверка в проверках.
2. Локальная настройка: `scripts/setup.sh` → задача mise → проверки и сторож → снятие
   `scripts/bootstrap.sh` → документы → повторный аудит.

Потребителю миграция не нужна: правило добавляется повторным запуском скрипта поставки.
Контрибьютору: вместо `scripts/bootstrap.sh` — `mise run setup`; прежние относительные ссылки
распознаются своими и пересоздаются при первом запуске.

Откат — возврат коммитов изменения: `scripts/bootstrap.sh` возвращается, объявления и правило
исчезают. Вне репозитория остаются ссылки в каталогах регистрации, хранилище и лаунчер — их снимают
`scripts/setup.sh --uninstall` и `scripts/install.sh --uninstall`.
