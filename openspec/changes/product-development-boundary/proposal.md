# Proposal

## Why

Одни и те же компоненты tessera и их описания служат двум разным целям — продукту и разработке
продукта, — и агент не различает, для какой из них они предназначены: в README плагина лежат
инструкции по расширению, `AGENTS.md` не отделяет правила-содержание продукта от правил-норм
работы над ним, а слово «разработчик» называет обе роли. Одновременно у разработки продукта нет
собственного механизма настройки: контрибьютор собирает харнесы вручную — `scripts/bootstrap.sh`
связывает только навыки плагина и только в каталогах проекта, а скрипт поставки ставит tessera
из ветки `main`, а не из рабочего дерева.

Разделение продукта и разработки продукта — не оформление проектной документации, а смысловая
часть разработки ПО класса «плагины»: продукт сам состоит из описаний для агентов и создаётся
через описания для агентов. Поэтому норма о нём заводится новым правилом — нормами классов ПО.

Изменение закрывает две задачи — [TSS-019](https://github.com/united-software-platform/tessera/issues/13)
и [TSS-020](https://github.com/united-software-platform/tessera/issues/14). Объединяющий смысл
по [GIT-005](../../../plugins/tessera-plugin/rules/git-rules.md#рабочая-ветка) — граница продукта
и разработки продукта: TSS-019 проводит её в описаниях артефактов, TSS-020 даёт разработке
продукта собственный механизм.

## What Changes

Предмет описания (TSS-019):

- Новое правило плагина «Нормы классов ПО» — `plugins/tessera-plugin/rules/software-class-rules.md`.
  Нормы ведутся по классам ПО, у класса своя серия кодов. Первый класс — плагины, ПО, поставляющее
  что-либо куда-либо: `PLG-001`…`PLG-008` о предмете описания. Правило действует и для самого
  tessera, и для проектов, получающих его поставкой; правил в плагине становится девять.
- Объявление предмета появляется у всех носителей для агентов: девять правил, четыре навыка,
  `AGENTS.md`, `README.md`, `CONTRIBUTING.md`, `GLOSSARY.md`, документ кейсов и README плагина.
- Смешания устраняются: разделы разработки («Как расширять», «Проверка», пункт о локальной
  регистрации) выходят из README плагина в `CONTRIBUTING.md`; `AGENTS.md` получает раздел
  о предметах и объявляет, что правила плагина — содержание продукта, принятое как нормы работы.
- Слова ролей приводятся к глоссарию: «разработчик» перестаёт называть роль — потребитель
  или контрибьютор.
- `scripts/check.sh` сверяет объявление предмета у каждого носителя.

Локальная настройка (TSS-020):

- Новый механизм для контрибьютора: `scripts/setup.sh` и задача mise `mise run setup`.
- **BREAKING** для контрибьюторов: `scripts/bootstrap.sh` снимается — его работу покрывает
  единый вход `scripts/setup.sh`.
- tessera не ставится для самой себя: навыки плагина связываются из рабочего дерева, компонентами
  являются только зависимости.
- Область установки задаётся параметром `--scope project|user`, умолчание — `project`.
- Дополнительно: `--plugin-only` (только навыки плагина, без зависимостей), `--harness`,
  `--skills-dir`, `--uninstall`.
- Правила не подключаются, реестр поставки локальная настройка не пишет.
- `scripts/install.sh` не меняется; `scripts/check.sh` сверяет общие блоки двух скриптов
  и исполняет дымовые прогоны локальной настройки.

Глоссарий и версия плагина:

- `GLOSSARY.md` пополняется статьями «Контрибьютор», «Класс ПО», «Предмет описания», «Продукт»,
  «Разработка продукта», «Локальная настройка»; «Область установки» и «Хранилище» обобщаются
  на поставку и локальную настройку.
- Версия tessera-plugin повышается до `0.8.0` — поставляемое содержимое меняется.

## Capabilities

### New Capabilities

- `artifact-subject`: предмет описания для агентов в ПО класса «Плагины» — два предмета,
  объявление предмета в описании, один предмет на артефакт, применение правил продукта к работе
  над репозиторием; норма поставляется в плагине и действует для самого tessera.
- `local-setup`: локальная настройка харнесов контрибьютора — навыки плагина из рабочего дерева
  и зависимости в заданной области установки, без установки tessera для самой себя.

### Modified Capabilities

- `continuous-integration`: проверки пополняются сверкой объявления предмета, сторожем общих
  блоков `scripts/setup.sh` и `scripts/install.sh` и дымовыми прогонами локальной настройки.
- `plugin-dependencies`: в требовании об установке зависимостей роль названа термином глоссария —
  потребитель вместо разработчика.
- `framework-essence`: инфраструктура разработки — OpenSpec и локальная настройка — не предъявляется
  потребителю; роль названа контрибьютором.

## Impact

- Код: новый `scripts/setup.sh`; новые проверки в `scripts/check.sh`; задача `setup`
  в `mise.toml`; удаление `scripts/bootstrap.sh`. `scripts/install.sh` не меняется.
- Документы: новое правило плагина; `AGENTS.md`, `README.md`, `CONTRIBUTING.md`, `GLOSSARY.md`,
  `docs/use-cases.md`, README плагина, восемь прежних правил, четыре навыка; манифесты плагина
  и каталог маркетплейса — версия `0.8.0`.
- Потребители: получают девятое правило и объявление предмета в правилах и навыках при следующем
  обновлении; поведение навыков и скрипта поставки не меняется.
- Задачи: закрывает #13 и #14.

Вне рамок:

- Другие классы ПО: нормы заведены только для плагинов; новый класс получает свой раздел, когда
  появится ПО, к которому действующие нормы не подходят.
- Шаблоны операций не получают объявления предмета — это заготовки порождения, а не описания;
  предмет объявляет навык, который ими пользуется.
- Организационная инфраструктура в шаблонах операций (`united-software-platform/.github`, кеш
  `~/.cache/wrsp/issue-templates`) — предмет отдельной задачи.
- Дерево поставки в `README.md` (`DGN-011`) — осознанное решение TSS-015 и TSS-016.
- Документация локальной настройки для потребителя: её читатель — контрибьютор, материал живёт
  в `CONTRIBUTING.md` по [DGN-001](../../../plugins/tessera-plugin/rules/project-docs-rules.md#роли-читателей-dgn-001).
