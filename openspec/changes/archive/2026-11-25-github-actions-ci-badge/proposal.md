# Proposal

## Why

Проверки репозитория — валидность манифестов, синтаксис и поведение скрипта поставки,
дымовые прогоны установки — запускаются только руками по разделу «Проверки» `CONTRIBUTING.md`:
правка попадает в `main` без машинного свидетельства, а состояние проверок читателю репозитория
нигде не видно. Скрипт поставки — единственный код репозитория и уже больше 1600 строк `bash`,
поэтому ручной прогон — слабая сеть для каждой правки. Задача — TSS-017 (issues/9).

## What Changes

- Заводится workflow GitHub Actions `.github/workflows/ci.yml` с именем `CI`: запускается
  на push в `main` и на `pull_request`, исполняет проверки репозитория и обходится без секретов —
  токен получает только чтение содержимого.
- Заводится `scripts/check.sh` — единая точка входа проверок: команды проверок 1–7 раздела
  «Проверки» `CONTRIBUTING.md` переносятся в него, workflow вызывает скрипт, а раздел «Проверки»
  называет скрипт одной командой. Перечень проверок живёт только в скрипте.
- Дымовые прогоны в скрипте ставят tessera из фиксации `HEAD` каталога репозитория, зависимости —
  из их репозиториев: прогон pull request проверяет правки навыков, правил и шаблонов до слияния,
  а не после него.
- `README.md` получает в блок бейджей бейдж состояния прогонов CI на `main` — нативный `badge.svg`
  GitHub Actions, значение читается из прогонов.
- `CONTRIBUTING.md`: класс «Состояние» в легенде и строка в карте бейджей; раздел «Проверки» —
  две команды вместо восьми; в таблице устройства — строки `.github/workflows/ci.yml`
  и `scripts/check.sh`.
- Заводится способность `continuous-integration`.

Ломающих изменений нет: поставка потребителю и содержимое плагина не меняются.

## Capabilities

### New Capabilities

- `continuous-integration`: автоматический прогон проверок репозитория на GitHub Actions —
  запуск на push и pull request, единая точка входа проверок, прогон без секретов, источник tessera
  в дымовых прогонах, бейдж состояния в `README.md`.

### Modified Capabilities

- Нет: требования `delivery`, `plugin-dependencies` и `framework-essence` не меняются. Скрипт
  поставки в прогонах не правится — меняется только среда, в которой его запускает скрипт проверок.

## Impact

- Код: новые `scripts/check.sh` и `.github/workflows/ci.yml`; `scripts/install.sh`
  и `scripts/bootstrap.sh` не меняются.
- Документы: `README.md` — бейдж и ограничение о чтении бейджами ветки `main`; `CONTRIBUTING.md` —
  легенда, карта бейджей, раздел «Проверки», таблица устройства, строка версий.
- Спецификации: новая `openspec/specs/continuous-integration/spec.md` появляется при архивации;
  дельт существующих способностей нет.
- Зависимости: workflow зависит от действия `actions/checkout` (закрепление мажором) и образа
  `ubuntu-latest` — `bash`, `git`, `python3`; дымовые прогоны читают публичные репозитории GitHub
  `united-software-platform/formular` и `mattpocock/skills` на `main`.
- Не затрагивается: содержимое плагина `plugins/tessera-plugin/` — версия плагина не поднимается;
  `GLOSSARY.md` — CI, как и OpenSpec, инфраструктура разработки самого репозитория, а не язык
  поставки.
- Вне рамок: обязательность зелёного прогона для слияния — защита ветки, настройка репозитория
  на GitHub, остаётся за владельцем; новые линтеры (`shellcheck`, `markdownlint`); задачи mise;
  Dependabot для действий.
