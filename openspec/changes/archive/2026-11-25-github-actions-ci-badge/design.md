# Design

## Context

Мотивация — в proposal.md, раздел Why. Здесь — состояние, из которого исходят решения.

- Проверки репозитория живут разделом «Проверки» `CONTRIBUTING.md` — восемь команд, которые
  правящий репозиторий запускает руками. Каталога `.github/` в репозитории нет: ни одного workflow.
- Скрипт поставки `scripts/install.sh` всегда клонирует источники из ветки `main` GitHub — таблица
  `COMPONENTS` и функция `ensure_sources`; запуск из клона меняет только способ получить скрипт
  (заголовок скрипта). Поэтому дымовой прогон, запущенный как есть, проверяет `install.sh` прогона
  против содержимого `main`.
- Скрипт поставки сам завершается с ненулевым кодом при неисправных ссылках, элементах правил
  и молчащем лаунчере (`install_supply`), поэтому код возврата — достаточный критерий прогона.
- `scripts/bootstrap.sh` — локальная настройка разработчика (раздел «Локальная настройка»
  `AGENTS.md`): безусловно регистрирует симлинки навыков в `.agents/skills` и `.claude/skills`
  репозитория и выходит с кодом `0`; критерия пройденности у неё нет.
- Блок бейджей `README.md` упорядочен по классам легенды `CONTRIBUTING.md` — поставка, зависимость,
  право, харнес; семантические цвета `green`/`yellow`/`red` в легенде зарезервированы под состояния.
- Проверено 2026-11-25 на машине разработки: обе дымовые команды проходят против `HEAD`
  репозитория с перенаправлением источника (решение 3) — код `0`, `backlog --help` отвечает через
  лаунчер, зависимости клонируются из GitHub.

## Goals / Non-Goals

**Goals:**

- Один перечень проверок, который потребляют и прогон, и документ.
- Прогон pull request проверяет правки содержимого плагина до слияния.
- Прогон без секретов, с минимальными правами токена.

**Non-Goals:**

- Обязательность зелёного прогона для слияния — защита ветки, настройка репозитория на GitHub.
- Новые линтеры, задачи mise, кеш зависимостей, матрица ОС, запуски по расписанию.
- Проверочные параметры скрипта поставки: он остаётся потребительским.
- Проверка незафиксированных правок рабочего дерева.

## Decisions

### 1. Workflow — одна задача с одним шагом проверок

`.github/workflows/ci.yml`: имя `CI`, запуск на `push` в `main` и на `pull_request`,
`permissions: contents: read`, одна задача на `ubuntu-latest` с `timeout-minutes: 15`; шаги —
`actions/checkout` и `scripts/check.sh`.

- Одна задача: проверки последовательны и длятся секунды плюс время клонирования.
- Событие `pull_request`, а не `pull_request_target`: код pull request исполняется с токеном,
  у которого есть только чтение содержимого; секретов в прогоне нет.
- `push` ограничен веткой `main`, поэтому push в ветку с открытым pull request не даёт второго
  прогона.
- Действие закреплено мажором — `actions/checkout@v7` (актуальный релиз v7.0.1 на 2026-11-25,
  мажор уточняется при реализации). Закрепление хешем коммита строже, но требует сопровождения
  обновлений; при токене без прав на запись и без секретов мажора достаточно.
- Имена шагов и вывод скрипта — на русском, как сообщения скриптов репозитория.

Альтернативы: шаг на проверку в workflow — дублирует перечень (решение 2); `workflow_dispatch`
и `schedule` — повторный запуск есть в интерфейсе Actions, а запуск по расписанию красит бейдж
`main` из-за изменений в чужих репозиториях без правки в этом.

### 2. `scripts/check.sh` — единая точка входа

`set -euo pipefail`, переход в корень репозитория, как в `bootstrap.sh`; обёртка печатает имя
проверки перед запуском, при ошибке называет непройденную и завершает скрипт с кодом `1`.

- Состав и порядок: быстрые статические проверки — манифест ZCode, идентичность манифестов,
  синтаксис `install.sh`, справка, реестр, — затем два дымовых прогона.
- Критерий каждого прогона — код возврата `0`: скрипт поставки сам завершается ненулевым кодом
  при неисправностях, разбор отчёта не нужен.
- Команды скрипта поставки идут с временным `HOME`: результат не зависит от хранилища и установок
  машины. Временные каталоги снимаются `trap`.
- `bootstrap.sh` в скрипт не входит: это действие локальной настройки, оно пишет в каталоги
  харнесов рабочего дерева.
- Параметров у скрипта нет: перечень несёт заголовок скрипта, а прогон называет каждую проверку
  выводом.

Альтернативы: задачи mise — ENV-006 относит к задачам окружения сервисы и инициализацию, а прогону
тогда нужен mise на runner'е; чтение перечня из `CONTRIBUTING.md` — хрупко; прогон всех проверок
со сводкой вместо остановки на первой непройденной — сводка требует накопления результатов,
а статические проверки идут первыми, так что большинство отказов видно сразу.

### 3. Дымовые прогоны берут tessera из `HEAD`

Перед дымовыми прогонами скрипт создаёт временное зеркало фиксации `HEAD` и перенаправляет адрес
tessera на него — только переменными окружения, на время двух команд:

```bash
git init --bare "$MIRROR"
git -C "$MIRROR" symbolic-ref HEAD refs/heads/main
git -C "$MIRROR" fetch --depth=1 "file://$REPO" HEAD:refs/heads/main
export GIT_CONFIG_COUNT=1
export GIT_CONFIG_KEY_0="url.file://$MIRROR.insteadOf"
export GIT_CONFIG_VALUE_0="https://github.com/united-software-platform/tessera.git"
```

- `--depth=1` у выборки обязателен: `actions/checkout` оставляет мелкий клон, и зеркало,
  созданное не мелким, отклоняет его ссылку — `shallow roots are not allowed to be updated`
  (наблюдалось в опыте).
- Конфигурация git через окружение, а не через параметр скрипта поставки: потребительский контракт
  не меняется, глобальная конфигурация git не трогается, перенаправление действует только внутри
  скрипта проверок.
- Ветка `main` в зеркале — требование `git clone --branch main`, которым скрипт ставит tessera.
- Контроль: после первого дымового прогона скрипт сравнивает `HEAD` клона tessera в хранилище
  с `HEAD` репозитория; расхождение — отказ с предложением сверить адрес tessera
  в `scripts/install.sh` и `scripts/check.sh`. Без контроля смена адреса в таблице `COMPONENTS`
  оставила бы перенаправление недействующим молча — прогон вернулся бы к ветке `main`.
- `HEAD`, а не рабочее дерево: в прогоне есть только зафиксированное состояние; локально то же —
  правку фиксируют до запуска.

Альтернативы: параметр скрипта поставки — источник tessera (проверочный шов в потребительском
скрипте и правка способности `delivery`); слепок рабочего дерева через `git stash create`
(не включает неотслеживаемые файлы); оставить ветку `main` (правки содержимого плагина замечают
после слияния — отклонено владельцем).

### 4. Бейдж состояния и его класс

- Разметка — нативный бейдж GitHub Actions: изображение `actions/workflows/ci.yml/badge.svg`,
  ссылка — на страницу прогонов того же workflow. Надпись бейджа — имя workflow (`CI`); состояния
  `passing`, `failing`, `no status`.
- Нативный бейдж вместо shields.io: значение читает сам GitHub, без посредника и его лимитов.
- Класс «Состояние»: легенда `CONTRIBUTING.md` уже резервирует семантические цвета
  `green`/`yellow`/`red` под состояния; строка класса и строка карты бейджей — по DGN-004.
- Место — последним в блоке: порядок блока повторяет порядок классов легенды. Первым в блоке
  (частая практика) бейдж не ставится ради этого порядка.
- Ограничение README «Бейджи читают ветку main» дополняется: бейдж проверок показывает последний
  прогон на `main`, прогон pull request в бейдж не попадает.

### 5. Документы

- `CONTRIBUTING.md`: раздел «Проверки» — две команды (`scripts/check.sh`,
  `bash scripts/bootstrap.sh`) и пояснение, где живёт перечень, что проверяют дымовые прогоны
  и когда запускается прогон; «Устройство репозитория» — строки workflow и скрипта; легенда
  и карта бейджей — строки класса «Состояние»; строка версий по DOC-022.
- `README.md`: бейдж и дополненное ограничение. Другие разделы не меняются: применяющему систему
  CI не нужен.
- Версия плагина не поднимается — содержимое плагина не меняется. Глоссарий не меняется: CI,
  как и OpenSpec, инфраструктура разработки репозитория, а не язык поставки.

## Risks / Trade-offs

- [Дымовые прогоны зависят от сети и от ветки `main` репозиториев formular и mattpocock/skills:
  разрыв у них красит прогон правки, которая его не вызвала] → Версии зависимостей не закреплены
  (ограничение README); журнал называет непройденную проверку, прогон повторяется после
  исправления у источника.
- [Образ `ubuntu-latest` подвижен: смена образа убирает нужный инструмент] → Прогону нужны `bash`,
  `git`, `python3` — базовые инструменты образа; при сбое образ закрепляется конкретной версией.
- [Перенаправление перестаёт действовать при смене адреса tessera] → Контроль совпадения `HEAD`
  после первого прогона — отказ, а не молчаливый откат к ветке `main`.
- [Мелкий клон и зеркало проверены только на машине разработки] → Задача 2.2 повторяет состояние
  runner'а локально; первый прогон на pull request ветки — приёмочная проверка на настоящем.
- [Бейдж показывает `no status` до первого прогона на `main`] → Ожидаемо: первый прогон на `main`
  идёт после слияния изменения.
- [Скрипт останавливается на первой непройденной проверке] → Быстрые проверки идут первыми;
  повторный запуск показывает следующую.
- [Локальный запуск не видит незафиксированных правок] → Ограничение названо
  в `CONTRIBUTING.md`: правку фиксируют до запуска.

## Migration Plan

1. Изменение аддитивное: заводится скрипт проверок, затем workflow, затем правятся документы.
1. Коммит и push ветки — по запросу владельца (GIT-015); прогон на pull request — первый
   настоящий прогон CI.
1. После слияния первый прогон на `main` переводит бейдж из `no status` в `passing`.
1. Откат — удалить workflow и бейдж, вернуть раздел «Проверки» из истории; скрипт проверок
   при этом остаётся рабочим локально.
