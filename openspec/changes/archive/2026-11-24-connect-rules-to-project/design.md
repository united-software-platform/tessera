# Design

## Context

Мотивация — в `proposal.md`, требования — в дельтах `specs/`. Здесь только то, что определяет
подход.

- `scripts/install.sh` не хранит состояния: состав прежней установки выводится из хранилища,
  ссылок и git. Режим проекта задаётся `--project`, корень проекта — текущий каталог. Диалог
  читает `/dev/tty`. Порядок установки: параметры, профиль, харнесы, план, подтверждение,
  источники, снятие лишних клонов, навыки, лаунчер, самопроверка, отчёт.
- Правила — восемь файлов `plugins/tessera-plugin/rules/*.md` в клоне tessera хранилища.
  Каждое открывается заголовком `# <название>`. Правила ссылаются друг на друга относительными
  ссылками `./<файл>.md#…`; `project-docs-rules.md` ссылается и на навык плагина.
- Хранилище — полные клоны ветки `main`. Новые инструменты недоступны: скрипту нужны только
  bash, git и curl.
- Норма сути (`framework-essence`) пока требует применять правила только навыками и запрещает
  автозагрузку. Изменение её пересматривает — см. дельту.

## Goals / Non-Goals

**Goals:**

- Подключённые правила действуют в любом окружении, куда скопирован репозиторий проекта,
  без хранилища машины.
- Текст `AGENTS.md` вне секции правил не меняется; секция узнаваема как ведущаяся скриптом
  и называет, кем и когда поставлена.
- Повторный запуск без изменений не оставляет в проекте ни одного отличия.
- Ручные правки копий правил не пропадают молча.

**Non-Goals:**

- Другие точки входа агентов (`CLAUDE.md`, каталоги правил харнесов) и хуки.
- Подстройка правил под проект и правила плагинов-зависимостей.
- Закрепление редакции tessera в проекте.

## Decisions

### 1. Правила попадают в проект копиями

Копия переносима: репозитерий проекта остаётся со своими правилами на другой машине и в CI.
Симлинки на хранилище, как у навыков, в коммите ломаются у всех, у кого нет хранилища, а ссылка
на путь хранилища в секции привязывает проект к машине.

Альтернативы: симлинки в проект (единство с регистрацией навыков — отклонено: непереносимо);
секция со ссылками на хранилище (отклонено по той же причине).

### 2. Каталог `.tessera/rules/` и одна точка входа — `AGENTS.md`

Каталог с именем инструмента показывает, кто им ведёт, и снимается одним удалением.
`AGENTS.md` — стандарт, читаемый харнесами без плагинов; секция в нём связывает правила
с агентами любого харнеса.

Альтернативы: `rules/tessera/` (смешивает поставленное с собственными правилами проекта);
каталоги правил отдельных харнесов (привязка к харнесу — вне изменения).

### 3. Секция ограничена HTML-комментариями со штампом

```markdown
<!-- delivery-tessera-20261123211145 -->

## Правила tessera

Секцию ведёт скрипт поставки tessera: правила подключены 2026-11-23 в 21:11:45. Правки внутри
секции не сохраняются — повторная установка перепишет её. Свои инструкции пишите вне секции.

Перед выполнением любой задачи агент обязан полностью прочитать перечисленные правила:

- [Правила документации](./.tessera/rules/documentation-rules.md)

<!-- /delivery-tessera-20261123211145 -->
```

Штамп `YYYYMMDDHHMMSS` — локальное время; в имени маркера он отвечает сразу на «кем» (tessera)
и «когда». Названия правил берутся из заголовков файлов — второй копии перечня нет. Ссылки
относительные, как требует
[DOC-015](../../../plugins/tessera-plugin/rules/documentation-rules.md#ссылки-doc-015);
[DOC-005](../../../plugins/tessera-plugin/rules/documentation-rules.md#разметка-markdown) запрещает
теги-элементы, а комментарий не элемент и при просмотре не отображается.

Альтернативы: секция от заголовка до следующего заголовка того же уровня (при переписывании
можно поглотить текст проекта, добавленный после секции); штамп в тексте заголовка (якорь
секции менялся бы при каждой записи).

### 4. Секция переписывается только при изменении, штамп — время последней записи

Секция собирается заново со штампом существующей. Текст совпал — файл не трогается; отличается
— секция заменяется со штампом текущего запуска. Повторный запуск без изменений не оставляет
в `AGENTS.md` отличий, а штамп остаётся честным: он показывает, когда содержание секции
менялось в последний раз. Ручная правка внутри секции — отличие: секция переписывается, правка
не сохраняется, о чём секция предупреждает своим текстом.

Альтернатива: переписывать при каждом запуске (каждый запуск оставлял бы в проекте отличие
в `AGENTS.md` — отклонено).

### 5. Выбор правил — параметром и в диалоге, после получения источников

`--rules all|none|<список имён через запятую>`; в диалоге показывается пронумерованный перечень
правил источников. Перечень скрипт берёт из клона tessera, которого до первой установки нет,
поэтому диалог о правилах идёт после получения источников — единственный путь для первой
установки и повторной. Умолчание без `--rules` — перечень, выведенный из копий проекта; копий
нет — все правила. Отключение (`none`) не запоминается: оно не оставляет следа, а писать
в `AGENTS.md` секцию об отсутствии правил или заводить файл состояния не стоит. Поведение
зафиксировано сценарием «Правила были отключены» в дельте.

Альтернативы: диалог до плана (на первой установке перечня ещё нет); запоминание `none`
секцией-заглушкой (отклонено).

### 6. Выбор точный: правила по ссылкам не подтягиваются

Потребитель получает ровно названное. Типичные перечни замкнуты по ссылкам (документация
и чтение документов ссылаются на git-процесс), а остальные ссылки отчёт называет, чтобы
недостающее правило можно было добавить. Отчёт перечисляет только ссылки между правилами;
ссылка правила на навык плагина — известное исключение, оно разобрано в рисках.

Альтернатива: транзитивное замыкание по ссылкам (приносило бы правила, которые потребитель
исключил намеренно — отклонено).

### 7. Своя копия узнаётся по истории клона, без файла состояния

Копия поставлена скриптом, когда её содержимое совпадает с какой-либо редакцией этого правила
в истории клона tessera. Не совпадает ни с одной — копия изменена вручную. Приём тот же, каким
скрипт отличает свои ссылки от чужих: состояние выводится из артефактов, копии остаются
дословными, файл состояния в проекте не заводится, новых инструментов не требуется.

Обращение с копиями повторяет обращение с клонами хранилища:

| Ситуация | Что делает скрипт |
|----------|-------------------|
| Копия в перечне, изменена вручную | Оставляет и называет в отчёте — как клон с локальными изменениями при обновлении |
| Копия исключена из перечня или правила нет в источниках, не изменена | Снимает и называет в отчёте — как устаревшая ссылка |
| Такая же копия, изменена вручную | Останавливает запуск до изменения проекта — как клон с локальными изменениями при смене профиля |
| Удаление поставки | Снимает, в диалоге и отчёте называет изменённые вручную |

Альтернативы: манифест с контрольными суммами в проекте (лишний файл и вторая правда
о поставленном составе); перезапись всегда (теряет ручные правки); сравнение только с текущим
источником (устаревшую копию не отличить от правленой — обновление каждый раз требовало бы
вопроса).

### 8. Повреждённая секция — остановка

Маркер без парного или две секции означают ручную правку файла. Скрипт останавливается
и называет причину, не выбирая, какой текст считать секцией.

### 9. Правила подключаются только с `--project`

Правилам нужен проект; без параметра проекта подключать их некуда. `--rules` без `--project` —
ошибка параметров, снятие — `--uninstall --project`, как у ссылок навыков проекта.

### 10. Норма сути: два пути применения правил

Секция правил проекта становится вторым путём применения правил рядом с навыками; каталог-навык
остаётся точкой входа везде, включая проекты без подключённых правил. Хуки по-прежнему
запрещены. Имя требования сохранено, чтобы архивация заменила его текст, а не заводила новое.

## Risks / Trade-offs

- [Маркеры-комментарии видны агентам как текст `AGENTS.md`] → Две короткие строки; взамен —
  устойчивый разбор секции при любой правке файла проекта.
- [Ссылка правила на навык плагина в копии повиснет] → Существующее свойство правил; отчёт
  называет ссылки только между правилами.
- [Правило окружения описывает зонтичный репозиторий и подходит не всякому проекту]
  → Выбор конкретных правил.
- [История клона переписана в репозитории tessera — прежние редакции правила исчезли]
  → Копии будут приняты за изменённые вручную: безопасная сторона, копия пропускается
  и называется; свежую копию даёт удаление прежней.
- [В проектах с действующей установкой `--project` следующий запуск подключит все правила]
  → Отмечено в предложении как BREAKING; `--rules none` возвращает проект к прежнему составу.
- [Диалог о правилах идёт после подтверждения плана] → Следствие решения 5; Enter подключает
  все правила.
- [Секция предписывает агенту читать правила до каждой задачи и расходует контекст]
  → Таково назначение подключения; объём регулируется выбором правил.

## Migration Plan

1. Реализовать скрипт и проверить его в прогонах на поддельном домашнем каталоге и поддельных
   проектах — `tasks.md`.
2. Обновить документы плагина и репозитория, поднять версию плагина.
3. После слияния — повторный запуск с `--project` в проектах, где нужны правила.

Откат: `scripts/install.sh --project --rules none` снимает секцию и копии, оставляя навыки;
`--uninstall --project` снимает поставку проекта целиком.

## Open Questions

- Нужен ли параметр пути к файлу точек входа (проекты, где `AGENTS.md` лежит не в корне).
  На спеку, подход и задачи не влияет — при необходимости добавляется отдельным изменением.
