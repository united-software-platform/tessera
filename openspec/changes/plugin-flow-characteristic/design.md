# Design

## Context

Мотивация — в proposal.md, раздел Why. Здесь — состояние, которое определяет подход.

- Правило `plugins/tessera-plugin/rules/software-class-rules.md` (1.0.0) содержит только
  нормы о предмете описания, PLG-001…PLG-008. Класс «Плагины» охарактеризован одной фразой —
  «ПО, поставляющее что-либо куда-либо» — в назначении и в таблице «Понятия». Правило
  самодостаточно: общие для класса понятия определяет в собственной таблице «Понятия», потому
  что поставляется потребителю без глоссария репозитория; `GLOSSARY.md` повторяет их статьями
  по видам ДДД (с версии 3.5.0).
- Состав плагина и его зависимости уже описаны прозой в трёх местах: README плагина (разделы
  «Структура» и «Зависимости»), навык-каталог `tessera-plugin` (разделы «Состав плагина»,
  «Зависимости», «Подключение»), корневой `README.md` (абзацы «Навыки и правила — несёт плагин
  tessera-plugin» и «Плагины-зависимости»). Перечни в них написаны вручную.
- Данные о потоках есть только у поставки: реестр `scripts/install.sh --registry` перечисляет
  навыки и правила с полем `component`; таблица `COMPONENTS` скрипта и раздел `components`
  реестра плоские. Слова «зависимость» в `scripts/install.sh` нет; `scripts/setup.sh` называет
  зависимостями строки `COMPONENTS` без tessera, и только это сверяет `scripts/check.sh`.
  Манифесты плагина зависимостей не несут: спека `plugin-dependencies` запрещает каталогу
  маркетплейса нести чужие плагины.
- Лаунчер `backlog` — CLI зависимости, но в корневом `README.md` он назван внутри абзаца
  о поставке навыков и правил, а в навыке-каталоге — в разделе «Подключение».
- В README плагина есть колонка «Минимальная версия» зависимостей; её значения не читает ни
  скрипт, ни проверка, а корневой `README.md` фиксирует ограничение «Версии зависимостей
  не закреплены».
- Ограничения: правка правила — изменение продукта, она идёт изменением OpenSpec и повышением
  версии плагина; правило не содержит порядка разработки tessera (PLG-007); термины глоссария
  идут с Avoid-списками; норма называется кодом со ссылкой и не пересказывается (DGN-010);
  объявления предмета в правиле и трёх описаниях сверяет `scripts/check.sh`.

## Goals / Non-Goals

**Goals:**

- Агент, прочитав норму классов ПО, узнаёт характеристику класса: два потока и что несёт каждый.
- Норма обязывает плагин объявлять состав плагина и зависимости плагина и называет, в носителях
  какого предмета живёт каждая зависимость.
- В tessera три описания называют оба перечня одними терминами и не смешивают потоки.

**Non-Goals:**

- Машиночитаемое объявление зависимостей плагина, изменения реестра и таблицы `COMPONENTS`,
  сверка перечней проверкой репозитория — по решению владельца это отдельная задача.
- Закрепление и проверка версий зависимостей.
- Порядок добавления зависимости в раздел «Расширение плагина» `CONTRIBUTING.md`: выравнивание
  ограничено тремя описаниями.
- Изменение норм о предмете описания и спек `artifact-subject`, `delivery`,
  `plugin-dependencies`, `local-setup`.

## Decisions

### 1. Потоки — нормы того же класса: PLG-009…PLG-011

Характеристика класса и обязанности плагина становятся тремя нормами таблицы «Плагины» того же
правила: PLG-009 — два потока, PLG-010 — состав плагина и зависимости плагина объявляются,
PLG-011 — потоки разведены. Три новых раздела идут после «Сверки объявлений», по порядку кодов,
а назначение правила и вводный абзац таблицы норм называют потоки сразу — читатель получает
характеристику класса до норм о предмете.

Альтернатива — отдельное правило о потоках. Отклонена: характеристика класса оказалась бы
отделена от остальных норм класса, а правило — десятым файлом в перечне точки входа,
навыка-каталога, реестра и проверок.

### 2. Названия: потоки — по направлению, перечни — по владельцу

Потоки называет владелец: «поток поставки» и «поток зависимостей». То, что несёт каждый поток,
названо по владельцу перечня: «состав плагина» и «зависимости плагина». Вариант «перечень
поставки» отклонён владельцем: в глоссарии уже есть «состав поставки» и «реестр поставки»,
третий термин со словом «поставки» слился бы с ними. «Состав плагина» к тому же уже так назван
в навыке-каталоге.

Термины определены дважды, как принято в правиле: общей формулировкой — в таблице «Понятия»
правила, статьями по видам ДДД — в глоссарии. Статья «Зависимость» расширяется: сегодня это
только чужой плагин, необходимый навыку, а в потоке зависимостей есть и правила, и иные
артефакты для работы над плагином. В статьях «Состав плагина» и «Состав поставки» оговаривается
различие: состав поставки перечисляет компоненты запуска скрипта, состав плагина — артефакты
самого плагина.

### 3. Зависимость живёт в носителе своего предмета

Поток зависимостей один, но его записи читают по-разному. Зависимость, без которой навык
не работает, нужна и потребителю, и контрибьютору — она объявляется в носителях предмета
«продукт». Зависимость только для работы над плагином — правила, принятые как нормы, и
инструменты — объявляется в носителях предмета «разработка продукта», как и сегодня: нормы
принятия объявляет точка входа агентов, инструменты — `CONTRIBUTING.md`.

Альтернатива — отнести весь поток зависимостей к разработке продукта. Отклонена владельцем:
она противоречит спекам `plugin-dependencies` и `artifact-subject`, по которым зависимости
ставит потребитель и отказ навыка един для обеих ролей.

### 4. В tessera перечни остаются в трёх описаниях

Состав плагина и зависимости плагина называются в README плагина, навыке-каталоге и корневом
`README.md`. Навык-каталог отвечает на вопрос о плагине, не читая других файлов, а корневой
`README.md` читает человек, который не открывает README плагина; одно место-источник со
ссылками из остальных лишило бы их этого. Плата за выбор — три ручные копии, риск расхождения
записан ниже.

Атомарная правка — носителем нормы становится README плагина: он один называет коды
PLG-010 и PLG-011 ссылками на правило. Раздел «Структура» переименовывается в «Состав
плагина»: он и есть объявление состава, а «структура» попадает в Avoid-список термина. Навык-
каталог указывает на норму строкой темы в таблице правил, корневой `README.md` называет только
термины — он адресован применяющему и норм кодами не цитирует.

### 5. Лаунчер `backlog` — артефакт потока зависимостей

Лаунчер ставится на машину получателя, но остаётся CLI зависимости. По PLG-011 он не входит
в состав плагина. В корневом `README.md` его упоминание переезжает из абзаца о навыках и
правилах в блок зависимостей; в навыке-каталоге — из раздела «Подключение» в «Зависимости».
В README плагина он уже назван в разделе «Зависимости». Дерево поставки в корневом `README.md`
не меняется: оно показывает, что оказывается на машине, и лаунчер в нём уже подписан как
«лаунчер CLI зависимости».

### 6. Минимальные версии остаются справочными

Колонка «Минимальная версия» в README плагина сохраняется и получает одну оговорку: скрипт
ставит ветку `main`, минимальные версии не проверяются. Это приводит README плагина
к ограничению «Версии зависимостей не закреплены» корневого `README.md`. Снять колонку
отклонено: она называет версии, с которыми зависимости проверялись.

### 7. Машинной сверки нет — и норма об этом говорит

Состав плагина и зависимости плагина сверяются чтением описаний; правило отмечает это
примечанием при PLG-011, как правило документов проекта отмечает отсутствие проверки каркаса.
В `scripts/check.sh` ничего не добавляется, носители перечней в сверку объявлений предмета
не входят — их объявления не меняются.

### 8. Версии

Плагин — 0.8.0 → 0.9.0 в обоих манифестах и в каталоге маркетплейса: новые нормы без
ломающих изменений. Правило — 1.0.0 → 1.1.0, глоссарий — 3.5.1 → 3.6.0, навык-каталог —
2.6.2 → 2.7.0, точка входа агентов — 1.1.1 → 1.2.0.

## Risks / Trade-offs

- [Три описания ведутся вручную и разойдутся] → термины и состав записей выравниваются одной
  правкой по каталогам `skills/`, `rules/`, `templates/` и таблице зависимостей; сверка
  перечней с данными скрипта — следующая задача владельца.
- [Артефакт в обоих потоках читается как нарушение разведения] → PLG-011 оговаривает случай
  явно, с примером правила, которое плагин и поставляет, и принимает для работы над собой.
- [Переименование раздела «Структура» ломает внешние ссылки на якорь] → на применении ссылки
  на `#структура` ищутся по репозиторию и переписываются; внешние ссылки на якорь README
  плагина неизвестны.
- [Норма класса проверена только на tessera] → другого плагина класса в репозитории нет;
  формулировки норм не несят частностей tessera — они живут в примерах и в описаниях.
- [Дымовые прогоны проверок видят только зафиксированное состояние] → статические проверки
  запускаются до фиксации, полный `scripts/check.sh` — после.

## Migration Plan

Миграции нет: меняются норма, описания и версия плагина. Применение идёт в рабочей ветке —
её создание требует явного запроса владельца. Откат — отменой коммита изменения; версию плагина
возвращать не нужно.

## Open Questions

- Код и номер задачи для колонки «Задача» таблиц версий и заголовков коммитов: уточняются
  у владельца до применения по GIT-010. На спеки, подход и состав задач не влияют.
