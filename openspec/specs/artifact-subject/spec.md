# artifact-subject Specification

## Purpose

Предмет описания для агентов в ПО класса «Плагины»: какое описание служит продукту, какое —
разработке продукта, и как агент различает их по самому описанию.

## Requirements

### Requirement: Норма класса поставляется и действует для самого tessera

Нормы класса ПО «Плагины» о предмете описания SHALL поставляться в плагине наравне с прочими
правилами и SHALL действовать для самого tessera: репозиторий объявляет предметы своих описаний
и сверяет объявления проверкой.

#### Scenario: Потребитель получает норму

- **WHEN** потребитель устанавливает tessera
- **THEN** правило норм классов ПО поставлено вместе с прочими правилами и названо в каталоге
  навыка `tessera-plugin`

#### Scenario: tessera подчиняется собственной норме

- **WHEN** контрибьютор запускает проверки репозитория tessera
- **THEN** объявление предмета сверено у каждого носителя для агентов

#### Scenario: Нормы ведутся по классам ПО

- **WHEN** появляется ПО другого класса, к которому действующие нормы не подходят
- **THEN** нормы для него заводятся отдельным разделом своего класса, не правкой норм плагинов

### Requirement: Описание для агентов принадлежит одному предмету

Описания для агентов SHALL принадлежать ровно одному из двух предметов: «продукт» — уровень
предмета, что описывается и как ведёт себя компонент; «разработка продукта» — уровень работы
над предметом, как компонент создаётся — правила и процесс.

#### Scenario: Описание навыка — предмет «продукт»

- **WHEN** агент открывает описание навыка плагина
- **THEN** описание объявляет предмет «продукт» — уровень предмета, поведение компонента

#### Scenario: Документ для контрибьютора — предмет «разработка продукта»

- **WHEN** агент открывает `CONTRIBUTING.md`
- **THEN** документ объявляет предмет «разработка продукта» — уровень работы над предметом,
  правила и процесс

### Requirement: Описание объявляет предмет сразу после заголовка

Каждое описание для агентов — правило плагина, навык плагина, точка входа агентов, README
и прочий документ репозитория, который читают агенты, — SHALL открываться объявлением предмета:
единственной канонической строкой сразу после заголовка, а для README с блоком бейджей —
после блока.

#### Scenario: Объявление в правиле

- **WHEN** агент открывает правило плагина
- **THEN** первой содержательной строкой после заголовка идёт каноническое объявление предмета
  «продукт»

#### Scenario: Объявление в README

- **WHEN** агент открывает корневой `README.md`
- **THEN** объявление предмета стоит сразу после блока бейджей, перед назначением

#### Scenario: Неканоничное объявление

- **WHEN** в описании объявление отсутствует, повторяется или отличается от канона
- **THEN** проверка репозитория не проходит и называет файл

### Requirement: Объявленный предмет соответствует носителю

Объявленный предмет SHALL соответствовать носителю: навыки и правила плагина, README плагина,
корневой `README.md` и документ кейсов объявляют «продукт»; точка входа агентов,
`CONTRIBUTING.md` и глоссарий объявляют «разработку продукта».

#### Scenario: Точка входа агентов

- **WHEN** агент открывает `AGENTS.md`
- **THEN** точка входа объявляет «разработку продукта»

#### Scenario: Чужой предмет у носителя

- **WHEN** в правиле плагина объявлен предмет «разработка продукта»
- **THEN** проверка репозитория не проходит и называет файл

#### Scenario: Документ кейсов

- **WHEN** агент открывает документ кейсов
- **THEN** документ объявляет «продукт»

### Requirement: Артефакт обслуживает один предмет

Артефакт и его описания SHALL обслуживать ровно один предмет: материал другого предмета
выносится в носитель своего предмета, а в источнике остаётся ссылка на новое расположение.

#### Scenario: README плагина без материала разработки

- **WHEN** потребитель читает README плагина
- **THEN** в нём нет порядка расширения плагина, проверок репозитория и локальной настройки,
  а эти материалы лежат в `CONTRIBUTING.md`

#### Scenario: Порядок расширения — у контрибьютора

- **WHEN** контрибьютор ищет порядок расширения плагина
- **THEN** он находит его в `CONTRIBUTING.md`

### Requirement: Правила продукта приняты как нормы работы над репозиторием

Точка входа агентов SHALL объявлять правила плагина содержанием продукта и называть их нормы,
принятые для работы над репозиторием. Сами правила плагина SHALL описывать только поведение
продукта и MUST NOT содержать порядка разработки tessera.

#### Scenario: Точка входа называет принятое

- **WHEN** агент открывает `AGENTS.md`
- **THEN** он видит, что правила плагина — содержание продукта, и перечень норм, обязательных
  для работы над репозиторием

#### Scenario: Правило без порядка разработки tessera

- **WHEN** агент читает правило плагина в репозитории tessera
- **THEN** правило не содержит указаний о разработке tessera

### Requirement: Навык описывает только поведение продукта

Навык плагина SHALL описывать только поведение продукта. Порядок подготовки харнесов к работе
над репозиторием tessera SHALL жить в точке входа агентов и в `CONTRIBUTING.md`, а не в навыке.

#### Scenario: В навыке нет локальной настройки

- **WHEN** агент читает описание навыка плагина
- **THEN** в нём нет локальной настройки репозитория tessera

#### Scenario: Отказ навыка един для обеих ролей

- **WHEN** навык останавливается отказом из-за недоступной зависимости
- **THEN** отказ называет команду скрипта поставки — одинаковую для потребителя и контрибьютора

#### Scenario: Порядок подготовки харнесов — у контрибьютора

- **WHEN** контрибьютор ищет, как подготовить харнесы к работе над tessera
- **THEN** он находит порядок в `CONTRIBUTING.md`

### Requirement: Роли названы терминами глоссария

В описаниях для агентов роль, применяющая tessera, SHALL называться «потребитель», роль, правящая
tessera в её репозитории, — «контрибьютор». Слово «разработчик» MUST NOT называть роль.

#### Scenario: Состав задаёт потребитель

- **WHEN** агент читает требование о зависимостях
- **THEN** роль, задающая состав, названа «потребитель»

#### Scenario: Локальную настройку выполняет контрибьютор

- **WHEN** агент читает порядок локальной настройки
- **THEN** его читатель назван «контрибьютор»

#### Scenario: Роли в глоссарии

- **WHEN** агент открывает `GLOSSARY.md`
- **THEN** он находит роли «Потребитель» и «Контрибьютор» со списками избегаемых синонимов
