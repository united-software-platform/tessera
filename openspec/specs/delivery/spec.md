# delivery Specification

## Purpose

Единый скрипт поставки tessera: доставка навыков, правил, шаблонов операций и зависимостей
в харнесы потребителя из одного запуска.

## Requirements


### Requirement: Одна команда ставит tessera

Скрипт поставки SHALL запускаться одной командой, которая скачивает его и выполняет, без
предварительного клона репозитория; запуск `scripts/install.sh` из клона SHALL давать тот же
результат. Источники SHALL раскладываться в хранилище `~/.local/share/tessera/`.

#### Scenario: Запуск одной командой

- **WHEN** потребитель выполняет в терминале команду скачивания и запуска скрипта без параметров
- **THEN** поставлены все компоненты в пользовательской области, а в терминале скрипт сначала
  показывает найденные харнесы и план установки для подтверждения

#### Scenario: Запуск из клона

- **WHEN** потребитель запускает `scripts/install.sh` из клона репозитория
- **THEN** установлен тот же состав из тех же источников, что и при запуске одной командой

### Requirement: Один механизм для любого харнеса

Для всякого харнеса скрипт SHALL работать одним способом: раскладывать источники в хранилище
и связывать навыки симлинками с каталогами навыков. Средства харнесов для установки плагинов
SHALL не использоваться.

#### Scenario: Навыки доступны по коротким именам

- **WHEN** установка завершена и сессия харнеса перезапущена
- **THEN** навыки доступны по коротким именам (`workflow-fast`, `backlog-generate`), а их файлы
  лежат только в хранилище

#### Scenario: Одинаковый результат в разных харнесах

- **WHEN** скрипт устанавливает один состав поставки в два поддерживаемых харнеса
- **THEN** в обоих доступны одни и те же навыки из одного хранилища

### Requirement: Ставится для всех проектов по умолчанию

Параметром запуска `--scope` потребитель SHALL выбирать область установки: `user` —
пользовательские каталоги харнесов, `project` — каталоги навыков текущего проекта. Умолчание —
`user`.

#### Scenario: Установка для всех проектов

- **WHEN** скрипт запущен без параметра области
- **THEN** ссылки создаются в пользовательских каталогах навыков, и навыки доступны в любом
  проекте потребителя

#### Scenario: Установка в проект

- **WHEN** скрипт запущен с `--scope project`
- **THEN** ссылки создаются в каталогах навыков текущего проекта, а пользовательские каталоги
  не меняются

#### Scenario: Неизвестная область

- **WHEN** `--scope` задан значением, не являющимся `project` или `user`
- **THEN** запуск останавливается с кодом `2`, ничего не меняя

### Requirement: Состав поставки задаётся перечнем компонентов

Состав поставки SHALL задаваться параметром запуска `--components` — перечнем имён компонентов
через запятую. Поставленными SHALL оказываться ровно названные компоненты: поставленные ранее
и не названные снимаются этим запуском. Перечень SHALL содержать хотя бы одно имя, и каждое имя
SHALL быть именем компонента таблицы скрипта.

#### Scenario: Состав без одной зависимости

- **WHEN** скрипт запущен с `--components tessera,mattpocock-skills`
- **THEN** поставлены tessera и mattpocock-skills, а formular не поставлен: его клона в хранилище
  нет, навыки backlog и лаунчер `backlog` отсутствуют

#### Scenario: Только зависимости

- **WHEN** скрипт запущен с `--components formular` в пользовательской области
- **THEN** поставлены навыки backlog и лаунчер `backlog`, а tessera не поставлен: его клона
  в хранилище нет и навыки tessera не связаны

#### Scenario: Смена состава снимает лишнее

- **WHEN** поставлены все компоненты, а повторный запуск задан с `--components tessera`
- **THEN** клоны зависимостей удалены, их навыки и лаунчер `backlog` сняты, а отчёт называет
  снятое

#### Scenario: Неизвестный компонент

- **WHEN** в перечне назван компонент, которого нет в таблице скрипта
- **THEN** запуск останавливается с кодом `2`, называет доступные компоненты и ничего не меняет

#### Scenario: Пустой перечень

- **WHEN** `--components` задан без значения или с перечнем без имён
- **THEN** запуск останавливается с кодом `2`, ничего не меняя

#### Scenario: Состав с удалением

- **WHEN** заданы `--components tessera` и параметр удаления
- **THEN** запуск останавливается с кодом `2`, ничего не меняя

### Requirement: Без параметров ставится полный состав

Когда параметр `--components` не задан, состав запуска SHALL включать все компоненты таблицы
скрипта — независимо от того, что было поставлено прежде.

#### Scenario: Первая установка без параметров

- **WHEN** скрипт запущен без параметров
- **THEN** поставлены все компоненты таблицы в пользовательской области

#### Scenario: Повторный запуск без параметров

- **WHEN** поставлены tessera и formular, а повторный запуск выполнен без `--components`
- **THEN** поставлены все компоненты: mattpocock-skills добавлен этим запуском

### Requirement: Снятые параметры отвергаются с подсказкой

Параметры профилей `--profile` и установки в проект `--project` SHALL сниматься: запуск с ними
SHALL останавливаться ошибкой параметров, а сообщение SHALL называть замену — `--components`
и `--scope project` соответственно.

#### Scenario: Прежняя команда с профилем

- **WHEN** скрипт запущен с `--profile backlog`
- **THEN** запуск останавливается с кодом `2`, а сообщение называет `--components`

#### Scenario: Прежняя команда с установкой в проект

- **WHEN** скрипт запущен с `--project`
- **THEN** запуск останавливается с кодом `2`, а сообщение называет `--scope project`

### Requirement: Харнесы определяются автоматически

Скрипт SHALL находить установленные харнесы и связывать навыки с каталогами всех найденных.
В диалоге найденный список SHALL показываться для подтверждения; параметром запуска его SHALL
можно ограничить; для харнеса вне списка SHALL приниматься путь к каталогу навыков.

#### Scenario: Найденные харнесы

- **WHEN** на машине найдены ZCode, Codex и Claude Code
- **THEN** скрипт предлагает связать навыки с `~/.agents/skills/` (ZCode и Codex) и
  `~/.claude/skills/` (Claude Code)

#### Scenario: Подтверждение в диалоге

- **WHEN** скрипт показывает найденные харнесы, и потребитель исключает один из них
- **THEN** каталог навыков исключённого харнеса не меняется

#### Scenario: Харнес вне списка

- **WHEN** потребитель передаёт путь к каталогу навыков харнеса, которого нет в списке
- **THEN** навыки связываются с этим каталогом

#### Scenario: Харнесы не найдены

- **WHEN** на машине не найден ни один харнес и путь к каталогу навыков не передан
- **THEN** скрипт сообщает об этом и завершается, ничего не меняя

### Requirement: Существующие файлы не перезаписываются молча

Существующий в каталоге назначения одноимённый навык, созданный не скриптом, скрипт SHALL
пропускать и сообщать о нём. Существующий файл лаунчера SHALL сохраняться резервной копией
до замены.

#### Scenario: Одноимённый навык

- **WHEN** в каталоге навыков уже есть элемент с именем устанавливаемого навыка, созданный
  не скриптом
- **THEN** скрипт оставляет его на месте и называет в отчёте

#### Scenario: Существующий лаунчер

- **WHEN** по пути лаунчера уже есть файл, созданный не скриптом
- **THEN** скрипт сохраняет его резервной копией рядом, ставит свой лаунчер и сообщает об этом

### Requirement: Лаунчер backlog ставится вместе с компонентом formular

Когда состав поставки включает компонент formular, скрипт SHALL помещать на PATH лаунчер
`backlog`, который задаёт `BACKLOG_HOME` на поставку backlog в хранилище и передаёт вызов ей.
Когда formular не входит в состав, лаунчер SHALL не создаваться, а при снятии formular из состава
поставленный лаунчер SHALL сниматься вместе с ним.

#### Scenario: Состав с formular

- **WHEN** установлен состав, включающий formular
- **THEN** команда `backlog` в новом сеансе терминала находит свою поставку без ручной настройки
  переменных окружения

#### Scenario: Состав без formular

- **WHEN** установлен состав, не включающий formular
- **THEN** лаунчер не создаётся

#### Scenario: Снятие formular из состава

- **WHEN** повторный запуск задал состав без formular, а лаунчер был поставлен скриптом
- **THEN** лаунчер снят, и отчёт называет это

### Requirement: Правила подключаются к проекту секцией AGENTS.md

При установке в проектной области скрипт поставки SHALL подключать правила плагина tessera-plugin
к текущему проекту: копировать каждое подключаемое правило в каталог правил проекта
`.tessera/rules/` и вести в `AGENTS.md` проекта секцию правил. Установка в пользовательской
области MUST NOT подключать правила.

#### Scenario: Первое подключение

- **WHEN** скрипт запущен с `--scope project` в каталоге проекта, где `AGENTS.md` уже есть
- **THEN** правила лежат копиями в `.tessera/rules/`, в `AGENTS.md` появилась одна секция правил,
  а остальной текст файла не изменился

#### Scenario: AGENTS.md отсутствует

- **WHEN** скрипт запущен с `--scope project` в каталоге проекта, где `AGENTS.md` нет
- **THEN** скрипт создаёт файл с заголовком, назначением и секцией правил

#### Scenario: Установка для всех проектов

- **WHEN** скрипт запущен в пользовательской области
- **THEN** в проектах не появляется ни копий правил, ни секции правил

#### Scenario: Секция повреждена

- **WHEN** в `AGENTS.md` есть маркер секции правил без парного либо две секции правил
- **THEN** скрипт останавливается сообщением об этом и не меняет файл

#### Scenario: Чужие элементы каталога правил

- **WHEN** в `.tessera/rules/` лежат элементы, поставленные не скриптом
- **THEN** скрипт оставляет их на месте и называет в отчёте

### Requirement: Проектная область требует tessera в составе

Область `project` SHALL требовать компонент `tessera` в составе запуска: подключаемые в ней
правила — часть tessera. Запуск в проектной области с составом без tessera SHALL останавливаться
ошибкой параметров до какого-либо изменения на диске.

#### Scenario: Состав без tessera в проектной области

- **WHEN** скрипт запущен с `--scope project` и `--components formular`
- **THEN** запуск останавливается с кодом `2`, ничего не меняя

### Requirement: Копия правила дословна

Копия правила SHALL быть дословной копией файла правила из источников. Копия считается изменённой
вручную, когда её содержимое не совпадает ни с одной редакцией этого правила, публиковавшейся
в источниках.

#### Scenario: Содержимое копии

- **WHEN** правило скопировано в проект
- **THEN** файл копии совпадает с файлом правила в хранилище

#### Scenario: Признак ручного изменения

- **WHEN** в файл копии правила в проекте внесены правки, которых нет ни в одной редакции правила
- **THEN** скрипт считает копию изменённой вручную

### Requirement: Секция правил называет поставку

Секция правил SHALL ограничиваться комментариями-маркерами `delivery-tessera-<штамп>`
и `/delivery-tessera-<штамп>`, где штамп — локальное время последней записи секции в виде
`YYYYMMDDHHMMSS`. В секции SHALL быть названы владелец — скрипт поставки tessera, время
подключения правил и перечень подключённых правил относительными ссылками на их копии.

#### Scenario: Содержимое секции

- **WHEN** правила подключены к проекту
- **THEN** секция заключена между маркерами с одним штампом, называет скрипт поставки tessera
  и время подключения, а каждая ссылка перечня относительная и ведёт на копию правила
  в `.tessera/rules/`

### Requirement: Секция правил переписывается только при изменении

Секция правил SHALL заменяться лишь тогда, когда её текст отличается от собранного заново
с прежним штампом: при отличии секция заменяется с новым штампом, при совпадении файл
не меняется. Ручные правки внутри секции отличием считаются и не сохраняются. Текст `AGENTS.md`
вне секции MUST оставаться неизменным при любой записи.

#### Scenario: Секция не изменилась

- **WHEN** повторный запуск собирает секцию с тем же текстом, что в файле
- **THEN** `AGENTS.md` не переписывается, и штамп секции прежний

#### Scenario: Секция изменена вручную

- **WHEN** текст внутри секции правил изменён вручную
- **THEN** секция переписана заново с новым штампом, правки не сохранены, а текст файла вне
  секции прежний

### Requirement: Правила выбираются параметром запуска --rules

Подключаемые правила SHALL выбираться: все, ни одного или перечень конкретных правил. Значение
задаётся параметром запуска `--rules`, а в диалоге — из перечня правил источников; без того
и другого в проекте без подключённых правил подключаются все. Неизвестное имя правила и `--rules`
в пользовательской области SHALL останавливать запуск ошибкой параметров, не меняя проект.

#### Scenario: Все правила по умолчанию

- **WHEN** скрипт запущен в проектной области в проекте без подключённых правил, а `--rules`
  не задан
- **THEN** подключены все правила источников

#### Scenario: Конкретные правила

- **WHEN** в `--rules` задан перечень имён правил
- **THEN** подключены только названные правила, а прочие в проект не попадают

#### Scenario: Без правил

- **WHEN** в `--rules` задано `none`
- **THEN** в проекте нет ни копий правил, ни секции правил

#### Scenario: Выбор в диалоге

- **WHEN** диалог показывает перечень правил источников, и потребитель называет часть правил
- **THEN** подключены названные правила

#### Scenario: Неизвестное правило

- **WHEN** в `--rules` названо правило, которого нет в источниках
- **THEN** запуск останавливается с кодом `2`, называет доступные правила и не меняет проект

#### Scenario: Правила вне проекта

- **WHEN** задан `--rules` в пользовательской области
- **THEN** запуск останавливается с кодом `2`, ничего не меняя

#### Scenario: Правила были отключены

- **WHEN** правила ранее были отключены значением `none`, а повторный запуск выполнен без `--rules`
- **THEN** подключаются все правила источников

### Requirement: Повторный запуск обновляет подключённые правила

Повторный запуск в проектной области SHALL приводить копии подключённых правил к состоянию
источников, сохраняя перечень подключённых правил, пока `--rules` не задал иной; без `--rules`
умолчанием служит перечень, выведенный из копий проекта. Копию, изменённую вручную, скрипт
SHALL оставлять на месте и называть в отчёте.

#### Scenario: Обновление правил

- **WHEN** потребитель повторно запускает скрипт в проектной области после изменения правила
  в источниках
- **THEN** копия правила совпадает с источником, а перечень подключённых правил прежний

#### Scenario: Запуск без изменений

- **WHEN** повторный запуск выполнен, а правила и их перечень не менялись
- **THEN** ни одна копия правила не переписана

#### Scenario: Прежний перечень по умолчанию

- **WHEN** повторный запуск без `--rules` выполнен в проекте, где подключена часть правил
- **THEN** подключены те же правила; в диалоге они предложены по умолчанию

#### Scenario: Копия изменена вручную

- **WHEN** копия подключённого правила изменена вручную
- **THEN** скрипт не перезаписывает её и называет в отчёте

### Requirement: Исключённые и устаревшие копии правил снимаются

Копию правила, не входящего в новый перечень либо отсутствующего в источниках, скрипт SHALL
снимать повторным запуском в проектной области, если она не изменена вручную. Если такая копия
изменена вручную, запуск SHALL останавливаться сообщением до какого-либо изменения проекта.

#### Scenario: Правило исключено из перечня

- **WHEN** новый перечень не включает правило, чья копия в проекте не изменена вручную
- **THEN** копия удалена, а секция правил переписана без него

#### Scenario: Правила нет в источнике

- **WHEN** правило исчезло из источников, а его копия лежит в проекте
- **THEN** копия снята и названа в отчёте

#### Scenario: Исключена изменённая копия

- **WHEN** новый перечень не включает правило, чья копия изменена вручную
- **THEN** запуск останавливается сообщением, и проект не меняется

### Requirement: Отчёт называет результат подключения правил

Отчёт установки SHALL называть состояние каждой копии правила — создана, обновлена, актуальна
или пропущена, — результат записи секции правил с её штампом и ссылки подключённых правил
на правила, которых в проекте нет.

#### Scenario: Отчёт о правилах

- **WHEN** установка с параметром проекта завершилась с подключёнными правилами
- **THEN** отчёт перечисляет каждую копию правила с её состоянием и называет результат записи
  `AGENTS.md` со штампом секции

#### Scenario: Ссылка на неподключённое правило

- **WHEN** подключённое правило ссылается на правило, не подключённое к проекту
- **THEN** отчёт называет эту ссылку

### Requirement: Отчёт называет состав поставки

Отчёт установки SHALL называть состав поставки именами компонентов. План «Будет сделано» SHALL
называть компоненты, которые запуск снимает, до подтверждения.

#### Scenario: Состав в отчёте

- **WHEN** установка выполнена с `--components tessera,mattpocock-skills`
- **THEN** отчёт называет tessera и mattpocock-skills

#### Scenario: План снятия

- **WHEN** повторный запуск в терминале задал состав без поставленного компонента
- **THEN** план до подтверждения называет этот компонент снимаемым

### Requirement: Реестр поставки печатается в JSON

Параметром `--registry` скрипт поставки SHALL печатать реестр поставки — описание всего, что
создаёт установка: компоненты с хранилищем, навыки, правила, секцию `AGENTS.md` и лаунчер.
Вывод SHALL быть валидным JSON и единственным выводом скрипта на стандартном выводе.

#### Scenario: Печать реестра

- **WHEN** скрипт запущен с параметром `--registry`
- **THEN** стандартный вывод содержит один JSON-документ с разделами компонентов, навыков,
  правил, точки входа и лаунчера и проходит разбор `python3 -m json.tool`

#### Scenario: Реестр одной командой

- **WHEN** скрипт запущен одной командой скачивания и запуска с параметром `--registry`
- **THEN** реестр напечатан так же, как при запуске из клона с теми же параметрами

### Requirement: Запись реестра называет имя, тип, путь и источник

Каждая запись реестра о создаваемом элементе SHALL называть имя, тип (`symlink` — ссылка
на навык, `copy` — копия правила, `section` — секция `AGENTS.md`, `wrapper` — лаунчер),
целевой путь и источник. Пути в домашнем каталоге и в проекте SHALL записываться относительно
`~` и корня проекта, чтобы реестр не зависел от машины и каталога запуска.

#### Scenario: Состав записи о навыке

- **WHEN** реестр напечатан для профиля с навыком `workflow-fast`
- **THEN** запись о навыке называет имя `workflow-fast`, тип `symlink`, целевой путь
  в каталоге навыков и источник — путь каталога навыка в хранилище

#### Scenario: Состав записи о правиле

- **WHEN** реестр напечатан с параметром проекта и правилом `cqrs`
- **THEN** запись о правиле называет имя `cqrs`, тип `copy`, целевой путь `.tessera/rules/cqrs.md`
  и источник — путь файла правила в хранилище

#### Scenario: Независимость от машины

- **WHEN** реестр напечатан в двух домашних каталогах и двух каталогах проектов
- **THEN** вывод совпадает, кроме полей времени и редакции источников

### Requirement: Реестр поставки отражает параметры запуска и не меняет диск

Реестр SHALL описывать установку, которую скрипт выполнил бы с теми же параметрами запуска:
состав поставки, область установки, харнесы, дополнительный каталог навыков и перечень правил.
Запуск с `--registry` SHALL завершаться, не создавая и не меняя ничего на диске и не начиная
диалога. Сочетание `--registry` с параметром удаления SHALL останавливать запуск ошибкой
параметров.

#### Scenario: Состав из одного tessera в реестре

- **WHEN** реестр напечатан с `--components tessera`
- **THEN** в нём навыки и правила только tessera, а лаунчер и компоненты зависимостей отмечены
  как не входящие в поставку

#### Scenario: Область проекта в реестре

- **WHEN** реестр напечатан с `--scope project` и без параметра области
- **THEN** в первом случае цели навыков лежат в каталогах проекта и описаны копии правил
  с секцией `AGENTS.md`, во втором — цели в пользовательских каталогах, а правил и секции
  в реестре нет

#### Scenario: Реестр не меняет диск

- **WHEN** скрипт запущен с `--registry` в домашнем каталоге без хранилища
- **THEN** после завершения хранилище, каталоги навыков и файлы проекта не созданы, код
  возврата `0`

#### Scenario: Реестр с параметром удаления

- **WHEN** скрипт запущен с `--registry` вместе с параметром удаления
- **THEN** запуск останавливается с кодом `2`, ничего не меняя

### Requirement: Реестр описывает состав и область без профилей

В реестре состав SHALL читаться по признаку входжения каждого компонента раздела компонентов,
а поле `scope` SHALL называть область запуска — `project` или `user`. Полей `profile` и `mode`
в реестре SHALL не быть.

#### Scenario: Состав в реестре

- **WHEN** реестр напечатан с `--components tessera,mattpocock-skills`
- **THEN** в разделе компонентов входящими отмечены только tessera и mattpocock-skills, а полей
  `profile` и `mode` в реестре нет

#### Scenario: Область в реестре

- **WHEN** реестр напечатан с `--scope project` и без параметра области
- **THEN** поле `scope` называет `project` в первом случае и `user` во втором

### Requirement: Реестр без источников печатается частично

Когда клонов в хранилище нет, скрипт SHALL печатать реестр частично: пути и уровни поставки
описаны, а перечни навыков и правил, берущиеся из источников, помечены как недоступные
до получения источников. Скрипт SHALL сообщать это в самом реестре и печатать его с кодом `0`.

#### Scenario: Хранилища нет

- **WHEN** скрипт запущен с `--registry` в домашнем каталоге без хранилища
- **THEN** реестр описывает компоненты, целевые каталоги, секцию `AGENTS.md` и лаунчер,
  а перечни навыков и правил помечены недоступными до получения источников

#### Scenario: Часть источников получена

- **WHEN** в хранилище есть клон tessera и нет клонов зависимостей
- **THEN** навыки и правила tessera перечислены, а перечни зависимостей помечены недоступными

### Requirement: Установка записывает реестр как факт

Установка SHALL записывать тот же реестр файлом `registry.json` в хранилище, а в проектной
области — ещё и в `.tessera/` проекта. Записанный реестр SHALL описывать установленное этой
установкой: состав поставки, область установки, харнесы, перечень навыков и подключённых правил.

#### Scenario: Реестр установки

- **WHEN** установка завершилась
- **THEN** в хранилище лежит `registry.json`, а его перечни совпадают с навыками и правилами
  отчёта установки

#### Scenario: Реестр состава

- **WHEN** установка выполнена с `--components tessera,mattpocock-skills`
- **THEN** `registry.json` отмечает включёнными tessera и mattpocock-skills

#### Scenario: Реестр проекта

- **WHEN** установка в проектной области завершилась
- **THEN** `.tessera/registry.json` проекта описывает цели навыков проекта, подключённые
  правила и секцию `AGENTS.md` со штампом

#### Scenario: Реестр обновляется

- **WHEN** установка повторена с другим перечнем правил
- **THEN** `registry.json` описывает новый перечень, а не прежний

### Requirement: Установка завершается самопроверкой

По окончании работы скрипт SHALL проверять каждую созданную ссылку, запуск CLI установленных
зависимостей, а при подключённых правилах — каждую ссылку секции правил и каждую записанную этим
запуском копию правила на совпадение с источником, печатать отчёт о том, что и куда поставлено,
и напоминать о перезапуске сессии харнеса. Отчёт SHALL называть путь записанного реестра.

#### Scenario: Отчёт об установке

- **WHEN** установка завершилась
- **THEN** скрипт печатает созданные ссылки и лаунчер с результатом проверки каждого
  и напоминание перезапустить сессию харнеса

#### Scenario: Неисправная ссылка

- **WHEN** созданная ссылка не разрешается в файл навыка
- **THEN** отчёт называет её неисправной, а скрипт завершается с ненулевым кодом возврата

#### Scenario: Неисправная ссылка секции правил

- **WHEN** ссылка секции правил не ведёт на файл копии правила в проекте
- **THEN** отчёт называет её неисправной, а скрипт завершается с ненулевым кодом возврата

#### Scenario: Копия не совпала с источником

- **WHEN** записанная запуском копия правила не совпадает с источником
- **THEN** отчёт называет её неисправной, а скрипт завершается с ненулевым кодом возврата

#### Scenario: Путь реестра в отчёте

- **WHEN** установка завершилась
- **THEN** отчёт называет путь `registry.json` в хранилище, а в проектной области — ещё и путь
  `.tessera/registry.json`

### Requirement: Повторный запуск обновляет установленное

Повторный запуск скрипта SHALL обновлять источники в хранилище до актуального состояния ветки
`main` и пересоздавать ссылки. Область запуска SHALL задаваться параметром `--scope`, состав —
параметром `--components`, а без него — всеми компонентами таблицы.

#### Scenario: Обновление

- **WHEN** потребитель повторно запускает скрипт с теми же параметрами после появления изменений
  в источниках
- **THEN** навыки и CLI зависимостей в хранилище соответствуют ветке `main`, а состав и цели
  установки прежние

#### Scenario: Локальные изменения в хранилище

- **WHEN** в одном из клонов хранилища есть незакоммиченные изменения
- **THEN** скрипт не обновляет этот источник и сообщает о нём

### Requirement: Удаление убирает созданное

Параметром запуска потребитель SHALL может удалить всё, созданное скриптом: ссылки, лаунчер
и хранилище, а в проектной области — секцию правил, копии правил и реестр текущего проекта.
Резервная копия прежнего лаунчера SHALL сохраняться, и скрипт SHALL сообщать её путь.

#### Scenario: Удаление

- **WHEN** потребитель запускает скрипт с параметром удаления
- **THEN** созданные скриптом ссылки и хранилище исчезают, лаунчер снимается, резервная копия
  прежнего лаунчера остаётся, и скрипт сообщает её путь

#### Scenario: Чужие навыки не затрагиваются

- **WHEN** в каталоге навыков рядом со ссылками скрипта лежат навыки, созданные не скриптом
- **THEN** удаление их не трогает

#### Scenario: Удаление в проекте

- **WHEN** скрипт запущен с параметром удаления в проектной области в каталоге проекта
  с подключёнными правилами
- **THEN** секция правил исчезает из `AGENTS.md`, копии правил удаляются, а остальной текст
  `AGENTS.md` не меняется

#### Scenario: Файл, созданный скриптом, остался без инструкций проекта

- **WHEN** после снятия секции правил в `AGENTS.md`, созданном скриптом, не остаётся инструкций
  проекта
- **THEN** файл удаляется

#### Scenario: Изменённые копии при удалении

- **WHEN** удаляются копии правил, изменённые вручную
- **THEN** в диалоге они названы до подтверждения, а в отчёте об удалении — после него

#### Scenario: Реестр при удалении

- **WHEN** поставка удалена
- **THEN** реестр проекта `.tessera/registry.json` исчезает вместе с хранилищем и его реестром

### Requirement: Шаблоны операций поставляются вместе с навыками

Шаблоны операций SHALL входить в поставку плагина. Навыки workflow SHALL сами передавать утилите
порождения беклога каталог шаблонов; шаблон операции в проекте SHALL иметь приоритет над
поставленным.

#### Scenario: Проект без своих шаблонов

- **WHEN** `workflow-fast` запускается в проекте, где нет файла `templates/workflow-fast.md`
- **THEN** используется шаблон из поставки плагина

#### Scenario: Проект со своим шаблоном

- **WHEN** `workflow-fast` запускается в проекте, где есть файл `templates/workflow-fast.md`
- **THEN** используется шаблон проекта
